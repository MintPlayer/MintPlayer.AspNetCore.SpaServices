# PRD: the `XSRF-TOKEN` cookie ships without `Secure` or `SameSite`, and the mint can take the whole response down

Upstream: [issue #85](https://github.com/MintPlayer/MintPlayer.AspNetCore.SpaServices/issues/85)
by @PieterjanDeClippel — *"Xsrf: the XSRF-TOKEN cookie has no Secure or SameSite, and RequestToken
is dereferenced unguarded inside OnStarting"*.

## Overview

`UseAntiforgeryGenerator()` writes the SPA-visible CSRF cookie with **`Path` and `HttpOnly` only**.
No `Secure`, no `SameSite`. It dereferences `tokens.RequestToken` unguarded, runs unprotected inside
a `Response.OnStarting` callback where a throw is swallowed by Kestrel and converted into a bare
500 with every header wiped, and — the part the issue understates — it calls
`IAntiforgery.GetAndStoreTokens` at the one moment in the request lifetime where that call is
guaranteed to rewrite `Cache-Control`, `Pragma` and `X-Frame-Options` on **every response the
application produces**.

Line 20 of [`AntiforgeryMiddleware.cs`](../MintPlayer.AspNetCore.SpaServices.Xsrf/AntiforgeryMiddleware.cs)
has been byte-for-byte unchanged since it was first committed in `cbe8006` (2023-11-18).

Three things make this worth more than a three-line patch:

1. **The defective code is at 100% line and 100% branch coverage.** `Xsrf` is the *best*-covered
   assembly in the solution. Seven tests in
   [`AntiforgeryMiddlewareTests.cs`](../MintPlayer.AspNetCore.SpaServices.Tests/Xsrf/AntiforgeryMiddlewareTests.cs)
   pin the current cookie exactly as written — including
   `Leaves_the_cookie_readable_by_script`, which asserts the *absence* of `httponly` and would go
   right on passing with `Secure` and `SameSite` still missing. Coverage did not catch any of this
   and was never going to; **the test suite pins the bug**.
2. **This package is already in conflict with another package in this same repository.**
   [PR #83](https://github.com/MintPlayer/MintPlayer.AspNetCore.SpaServices/pull/83) deliberately
   made prerendering *preserve* `Cache-Control`
   ([`SpaPrerenderingOptions.cs:100-106`](../MintPlayer.AspNetCore.SpaServices.Prerendering/Prerendering/SpaPrerenderingOptions.cs)
   documents the reasoning). Because Kestrel pops `OnStarting` callbacks LIFO and this middleware is
   registered first by design, its callback runs **last** and overwrites that preserved value with
   `no-cache, no-store`. The two packages work against each other, and Xsrf wins.
3. **There is a concrete, evidenced consumer waiting on it.**
   [MintPlayer.Spark](https://github.com/MintPlayer/MintPlayer.Spark) has declined to adopt this
   package twice, in writing, *only* over the cookie flags — and its own A/B test measures this
   package's `OnStarting` placement as strictly better than what Spark does today. See
   [*The consumer contract*](#the-consumer-contract-what-spark-actually-needs).

## The code, in full

[`MintPlayer.AspNetCore.SpaServices.Xsrf/AntiforgeryMiddleware.cs:12-26`](../MintPlayer.AspNetCore.SpaServices.Xsrf/AntiforgeryMiddleware.cs):

```csharp
public async Task Invoke(HttpContext httpContext)
{
	httpContext.Response.OnStarting((state) =>
	{
		var context = (HttpContext)state;
		//if (string.Equals(httpContext.Request.Path.Value, "/", StringComparison.OrdinalIgnoreCase))
		//{
		var tokens = antiforgery.GetAndStoreTokens(httpContext);
		httpContext.Response.Cookies.Append("XSRF-TOKEN", tokens.RequestToken, new CookieOptions() { Path = "/", HttpOnly = false });
		//}
		return Task.CompletedTask;
	}, httpContext);

	await next(httpContext);
}
```

### Provenance: this is *not* Microsoft's code

counterpart in `Microsoft.AspNetCore.SpaServices.Extensions`. The `// You may need to install the
Microsoft.AspNetCore.Http.Abstractions package into your project` comment on line 6 is the Visual
Studio **"Middleware Class" item template** boilerplate. The file was authored here.

Only three commits have ever touched it — `cbe8006` (#52, added), `226c27a` (#55, file-scoped
namespace + tabs), `201d9a6` (#69, `[Inject]` source generator, `UseAntiforgery` →
`UseAntiforgeryGenerator`). **None of them changed the cookie.** The commented-out path check on

The constructor is generated by `MintPlayer.SourceGenerators` into

## Verification: the issue's six claims, checked against source

Everything below was verified against `dotnet/aspnetcore` `release/10.0` @ `ad6ce5f8` and
`release/11.0` @ `5190a3e5`, matching the two TFMs this package targets. **Nothing relevant to any
claim differs between .NET 10 and .NET 11** — `FireOnStarting`, `OnStarting`, `ProduceEnd`,
`SetErrorResponseHeaders`, `CheckSSLConfig`, `SetDoNotCacheHeaders`, `AntiforgeryTokenSet` and
`ResponseCookies` are byte-identical across the two branches.

| # | Claim | Verdict |
|---|---|---|
| 1 | No `Secure` | ✅ **Confirmed** |
| 2 | No `SameSite` | ✅ **Confirmed** — with a correction to the consequence |
| 3 | `RequestToken` dereferenced unguarded | ⚠️ **Downgraded** — real, but not reachable with the built-in `IAntiforgery` |
| 4 | A throw in `OnStarting` becomes a bare 500 | ✅ **Confirmed, and worse than described** |
| 5 | `GetAndStoreTokens` clobbers cache headers, LIFO makes it load-bearing | ✅ **Confirmed** — and it is a live conflict *inside this repo* |
| 6 | The `state` parameter is unused | ✅ **Confirmed** |

### 1. No `Secure` — confirmed

`CookieOptions.Secure` defaults to `false`, so the cookie is sent on every `http://` request to the
origin. `HttpOnly = false` is correct and mandatory — Angular's `HttpXsrfCookieExtractor` reads
`document.cookie`, and RFC 6265bis §5.8.3 excludes `HttpOnly` cookies from non-HTTP retrieval — but
it means transport is the token's only protection, and there is none.

### 2. No `SameSite` — confirmed, but the consequence needs restating

`CookieOptions.SameSite` defaults to `SameSiteMode.Unspecified`, which emits **no attribute**, so
current browsers apply Lax-by-default. The issue is right that this is the browser's choice rather
than the application's. It is **not** right that `SameSite=Strict` "is what makes the double-submit
pattern hold up".

The server never reads the `XSRF-TOKEN` cookie off the wire. It reads the HttpOnly
`.AspNetCore.Antiforgery.<hash>` cookie and compares it to the `X-XSRF-TOKEN` *header*. The
JS-readable cookie is a **transport mechanism to the SPA**, not a credential. What defeats a
cross-site POST is that the attacker cannot set a custom header on a cross-origin `fetch` without a
CORS preflight, and cannot read `document.cookie` across origins. `Strict` on this half buys
marginal anti-exfiltration hardening on a value that is deliberately exposed to JavaScript anyway.

The half where `SameSite` genuinely matters is the framework's, and there the default is already
`Strict` — [`AntiforgeryOptions.cs`](https://github.com/dotnet/aspnetcore/blob/main/src/Antiforgery/src/AntiforgeryOptions.cs):

```csharp
private CookieBuilder _cookieBuilder = new CookieBuilder
{
    SameSite = SameSiteMode.Strict,
    HttpOnly = true,
    IsEssential = true,
    // ... relaxing the restriction on secure policy on some cookies by setting to 'None'.
    SecurePolicy = CookieSecurePolicy.None,
};
```

Two consequences worth putting on the record:

- **The framework's own antiforgery cookie ships without `Secure` even over HTTPS, by default.**
  That is a larger exposure than anything on the JS-readable half, and this package cannot fix it —
  it belongs to `AddAntiforgery`. The README should say so.
- Setting `SameSite=Strict` on this package's cookie **to match** the framework's is cargo-culting;
  the two halves have different jobs. It is still a reasonable *default* — see
  [Open decision 1](#open-decisions).

### 3. `tokens.RequestToken` unguarded — real, but downgraded

Both halves of the mechanism check out. `AntiforgeryTokenSet`'s constructor null-checks only
`formFieldName`, and `RequestToken` is genuinely `string?`. `ResponseCookies.Append` does not guard
`value` explicitly; the `ArgumentNullException` comes from `Uri.EscapeDataString`, so **its
`ParamName` is `"stringToEscape"`, not `"value"`** — a test asserting the parameter name would fail.

But tracing `GetAndStoreTokens` → `GetTokensInternal` → `Serialize`, the returned
`NewRequestTokenString` comes from `IAntiforgeryTokenSerializer.Serialize`, declared with a
non-nullable return and always returning Base64 or throwing. `Serialize` even asserts
`Debug.Assert(antiforgeryFeature.NewRequestToken != null)`.

**With the built-in `DefaultAntiforgery`, `GetAndStoreTokens(...).RequestToken` is never null.** The
`string?` is a nullable-annotation artifact of `IAntiforgeryFeature.NewRequestTokenString`. A null
requires a *custom* `IAntiforgery` — or a custom `IAntiforgeryTokenSerializer` breaking its own
contract — registered in DI.

The guard is still worth adding: it is one line, it satisfies nullable analysis, and it is honest
insurance against a replaced `IAntiforgery`. **The PRD must not claim the framework can hand you
null**, and the fix must not be justified on that basis.

### 4. A throw inside `OnStarting` — confirmed, and the real behaviour is worse

[`HttpProtocol.cs:810-835`](https://github.com/dotnet/aspnetcore/blob/release/10.0/src/Servers/Kestrel/Core/src/Internal/Http/HttpProtocol.cs),
with Microsoft's own comment stating the intent:

```csharp
static async Task ProcessEvents(HttpProtocol protocol, Stack<KeyValuePair<Func<object, Task>, object>> events)
{
    // Try/Catch is outside the loop as any error that occurs is before the request starts.
    // So we want to report it as an ApplicationError to fail the request and not process more events.
    try
    {
        while (events.TryPop(out var entry))
        {
            await entry.Key.Invoke(entry.Value);
        }
    }
    catch (Exception ex)
    {
        protocol.ReportApplicationError(ex);
    }
}
```

`TryPop` is destructive, so abandoned callbacks are gone rather than deferred. `ProduceEnd` then
reaches `SetErrorResponseHeaders`, and "all headers reset" is literal:

```csharp
private void SetErrorResponseHeaders(int statusCode)
{
    StatusCode = statusCode;
    ReasonPhrase = null;
    var responseHeaders = HttpResponseHeaders;
    responseHeaders.Reset();
    ResponseTrailers?.Reset();
    // ... Date, ContentLength = 0, optional Server
}
```

The wire response is `500`, no reason phrase, `Content-Length: 0`, and only `Date` (plus `Server`).
**Every `Set-Cookie` the application staged is destroyed** — including the antiforgery cookie half
and any sign-in cookie.

Three corrections to the issue's account:

- **"`UseExceptionHandler` cannot see it" is true only on the common path.** When the callbacks fire
  at end-of-request (nothing wrote to the body), the pipeline has already unwound. But if the
  application writes or calls `Response.StartAsync()`, `VerifyInitializeState` observes the stored
  exception and throws an **`ObjectDisposedException` wrapping the original** back into application
  code. Middleware sees a different exception type, and cannot recover: `HasStarted` never becomes
  `true`, so `ExceptionHandlerMiddlewareImpl` loops into another failed write.
- **If the response has already started, no 500 is possible at all.** `ProduceEnd` returns early,
  disables keep-alive and closes the connection — on HTTP/1.1 the client gets a truncated body; on
  HTTP/2, `Http2Stream.OnErrorAfterResponseStarted` sends `RST_STREAM`.
- **The servers do not agree.** IIS swallows identically (`IISHttpContext.FireOnStarting`, catch
  outside the loop, `SetErrorResponseHeaders` → `HttpResponseHeaders.Clear()`). **HttpSys does not
  swallow** — `NotifiyOnStartingAsync` has no try/catch at all. **Neither does TestServer** —
  `ResponseFeature.FireOnSendingHeadersAsync` uses `finally`, not `catch`, and
  `HttpContextBuilder.Abort` does `_responseTcs.TrySetException(exception)`.

> **This last point governs how the fix can be tested.** Under `TestServer`,
> `await client.GetAsync(...)` **throws the original exception**; it never returns the bare 500.
> A regression test for this defect written on any in-memory harness cannot reproduce Kestrel's
> behaviour. This is why the plan carries [Spike 1](./PLAN-Xsrf-Cookie-Hardening.md#spikes) rather
> than a test.

For completeness: the repo's own harnesses are *also* unable to see it. A bare
`Microsoft.AspNetCore.Http.Features.HttpResponseFeature` discards `OnStarting` callbacks entirely
(empty body, `HasStarted` hardcoded `false`), which is why all three of the repo's fakes exist.

### 5. Cache-header clobbering — confirmed, and it is a live conflict inside this repo

[`DefaultAntiforgery.GetAndStoreTokens`](https://github.com/dotnet/aspnetcore/blob/main/src/Antiforgery/src/Internal/DefaultAntiforgery.cs):

```csharp
if (!httpContext.Response.HasStarted)
{
    // Explicitly set the cache headers to 'no-cache'. This could override any user set value but this is fine
    // as a response with antiforgery token must never be cached.
    SetDoNotCacheHeaders(httpContext);
}
```

And `HasStarted` is `false` inside an `OnStarting` callback by construction — `HasResponseStarted`
is `_requestProcessingStatus >= HeadersCommitted`, and the only writer of `HeadersCommitted` is
`ProduceStart`, which runs strictly after `FireOnStarting` in every entry point. The clobber is not
incidental; the current design guarantees it fires on every response.

Two refinements the issue does not have:

- **It is not unconditional.** `SetDoNotCacheHeaders` leaves an existing `Cache-Control` alone if it
  already parses as *both* `no-cache` and `no-store`, and leaves an existing `Pragma: no-cache`
  alone. Everything else is overwritten, and `_logger.ResponseCacheHeadersOverridenToNoCache()`
  fires. Note the warning only logs when a *pre-existing* header was overridden — creating one from
  nothing is silent, which is the common case.
- **LIFO is confirmed on all four servers, but not all by a `Stack`.** Kestrel and IIS push onto a
  `Stack<KeyValuePair<…>>`. HttpSys uses a `List` iterated backwards with the comment
  `// Execute last to first. This mimics a stack unwind.` TestHost chains nested closures,
  newest-outermost. Same order, three mechanisms — the PRD should not say "it is a Stack".

**The in-repo conflict.** Grepping the whole repository, the *only* runtime writer of
`Cache-Control` in the pipeline is `GetAndStoreTokens` inside this callback. Static-file
configuration sets none; there is no `OnPrepareResponse` anywhere. Meanwhile
[`SpaPrerenderingOptions.cs:100-106`](../MintPlayer.AspNetCore.SpaServices.Prerendering/Prerendering/SpaPrerenderingOptions.cs)
records the deliberate #83 decision:

> Caching headers are preserved by default, because `StaticFileMiddleware` sets none of its own and
> the value present is normally the one upstream middleware intended.

`Cache-Control` is not in `DefaultDroppedResponseHeaders`, and
`ResponseHeaderPreservationTests.cs:137-143` pins that it survives prerendering. Xsrf registers
earliest, so its callback fires last, so it overwrites the value prerendering just protected.
`Demo/Prerendering/Demo.Web/Startup.cs:97` calls `app.UseResponseCaching()` — an application
combining that demo's pipeline with `UseAntiforgeryGenerator()` loses its caching policy on every
response, silently.

Neither demo currently combines the two, and no test does either, which is why nobody has seen it.

### 6. The unused `state` parameter — confirmed

`var context = (HttpContext)state;` is assigned and never read; the closure captures `httpContext`
(lines 19-20). The `state` overload exists precisely to avoid a closure allocation per request, and
the current code pays for both. This matters slightly more than cosmetics here because the package
sets `<PublishAot>true</PublishAot>`.

## Five further defects the issue does not mention

### A. `GetAndStoreTokens` also writes `X-Frame-Options: SAMEORIGIN`

`SaveCookieTokenAndHeader` sets it unless `AntiforgeryOptions.SuppressXFrameOptionsHeader`. It is a
third header mutation the package performs on every response without documenting it. Additive
rather than clobbering, so lower severity — but consumers who unknowingly rely on it would lose it
if the mint is ever gated.

### B. `SaveCookieTokenAndHeader` is **not** guarded by `HasStarted`

The `!HasStarted` check guards only `SetDoNotCacheHeaders`. The cookie append and the
`X-Frame-Options` write are unguarded. If the response has already started, both hit a read-only
`IHeaderDictionary` and throw `InvalidOperationException` — from inside the `OnStarting` callback,
into the swallow described in claim 4. A genuine unguarded throw path, and unlike the null
`RequestToken` it is reachable.

### C. ⚠️ `CheckSSLConfig` behind a TLS-terminating proxy — a live production failure today

```csharp
private void CheckSSLConfig(HttpContext context)
{
    if (_options.Cookie.SecurePolicy == CookieSecurePolicy.Always && !context.Request.IsHttps)
    {
        throw new InvalidOperationException(Resources.FormatAntiforgery_RequiresSSL(...));
    }
}
```

> `The antiforgery system has the configuration value AntiforgeryOptions.Cookie.SecurePolicy = Always, but the current request is not an SSL request.`

`CheckSSLConfig` is the first statement of `GetAndStoreTokens`. `Request.IsHttps` is derived purely
from `Request.Scheme`, which behind nginx / Traefik / a container ingress is `http` unless
`UseForwardedHeaders` is enabled **with** `ForwardedHeaders.XForwardedProto` **and** the proxy
passes the default loopback-only `KnownProxies`/`KnownNetworks`.

So an application that follows Microsoft's own documented advice —

```csharp
if (!builder.Environment.IsDevelopment())
{
    builder.Services.AddAntiforgery(o => { o.Cookie.SecurePolicy = CookieSecurePolicy.Always; });
}
```

— and deploys behind a TLS-terminating proxy gets an `InvalidOperationException` thrown from inside
an `OnStarting` callback on **every request**, surfacing as an unexplained blank 500 with all
headers stripped. This is reproducible against the current package without changing a line of it,
and it is the strongest argument for the try/catch. Spark's own `CodeCoverage` deployment
(`docker-compose.yml`, plain HTTP :8080 behind Traefik with `tls.certresolver=letsencrypt`) is
exactly this shape.

Neither `UseForwardedHeaders` nor `UseCookiePolicy` is called anywhere in this repository.

### D. The README documents the missing flags as if they were a decision — and is wrong twice

[`README.md:253`](../MintPlayer.AspNetCore.SpaServices.Xsrf/README.md):

> The cookie is written with `Path=/` and without `Secure` or an explicit `SameSite` value, so the
> framework's cookie policy defaults apply.

There is no "framework cookie policy default" that applies — `CookiePolicyMiddleware` only runs if
the application calls `UseCookiePolicy()`, which nothing here does. Absent that, the attributes are
simply absent and the *browser's* default applies. The sentence reads as a deliberate design
choice, which is how a reader would come to believe the flags were considered and rejected.

`RELEASE-NOTES.txt` is also stale: its newest section is `v 10.2.2` while the package ships
`11.0.0-rc.1`.

### E. The middleware holds `IAntiforgery` captive on the root provider

`UseMiddleware<Antiforgery>()` builds the instance once at pipeline-build time and resolves
constructor parameters from `ApplicationServices` — the root provider. Not a live defect, because
`AddAntiforgery` registers `IAntiforgery` as a singleton and `DefaultAntiforgery` takes the
`HttpContext` per call. But it is the captive-dependency *shape*: a scoped decorator over
`IAntiforgery` would be captured for the application's lifetime. The generated `[Inject]`
constructor cannot express method injection, so fixing it means dropping the source generator for
this type in favour of `Invoke(HttpContext context, IAntiforgery antiforgery)`.

## What `Secure = Request.IsHttps` does and does not buy

The issue proposes `Secure = httpContext.Request.IsHttps`. That is exactly
`CookieSecurePolicy.SameAsRequest`, which is what `CookieBuilder.Build` computes:

```csharp
Secure = SecurePolicy == CookieSecurePolicy.Always
      || (SecurePolicy == CookieSecurePolicy.SameAsRequest && context.Request.IsHttps),
```

| Option | Breaks plain-HTTP dev? | Silently ships non-`Secure` in production? |
|---|---|---|
| `Request.IsHttps` (≡ `SameAsRequest`) | No | **Yes** — behind an unconfigured proxy |
| Hardcoded `true` | **Yes** on `http://192.168.x.x`, `myapp.local`, HTTP intranet (localhost is exempt per MDN) | No |
| `CookieSecurePolicy` option, default `SameAsRequest` | No | Yes, same silent gap |
| Delegate to `AntiforgeryOptions.Cookie.SecurePolicy` | Depends on app | **Yes — that option defaults to `None`**, and `Always` triggers defect C |
| Rely on `UseCookiePolicy` | No | Yes if the app never calls it |

`UseCookiePolicy` is worth a note because it is commonly assumed not to work here, and it does:
`CookiePolicyMiddleware` does not post-process, it swaps `IResponseCookiesFeature` for the whole
request, so a cookie appended inside an `OnStarting` callback still goes through
`ResponseCookiesWrapper.ApplyPolicy` and its upgrade-only `Secure`/`SameSite` promotion. Good as a
*composable* answer, useless as the only one.

**No option is both safe by default and silent.** The design move that satisfies both constraints is
a `SameAsRequest` default **plus a loud one-time warning** when the cookie is about to be written
non-`Secure` on what does not look like a development host, naming `UseForwardedHeaders` and
`ASPNETCORE_FORWARDEDHEADERS_ENABLED` in the message. Precedent exists inside `DefaultAntiforgery`
itself, which logs `ResponseCacheHeadersOverridenToNoCache` for exactly this "we silently changed
something you would care about" reason.

## `GetTokens` vs `GetAndStoreTokens`: the tempting fix that is a trap

`IAntiforgery.GetTokens(HttpContext)` is public, supported, and **pure with respect to the
response** — no cookie, no `X-Frame-Options`, no `Cache-Control`, no `Pragma`. It looks like a
free fix for defect 5. It is not.

"Store" means *write the HttpOnly cookie half*. `GetCookieTokens` decides whether one is needed:
if the inbound cookie token is present and `IsCookieTokenValid`, `NewCookieToken` is `null` and
nothing needs writing. Otherwise it generates a fresh cookie token in memory, and `GetTokensInternal`
binds the returned `RequestToken` to **that** token.

> `GetTokens` is sufficient **if and only if** the request already carried a cookie token that
> `IsCookieTokenValid` accepts.
>
> Otherwise it is catastrophic: you hand the SPA an `XSRF-TOKEN` bound to a cookie token that is
> then thrown away. Every subsequent mutating request fails the `SecurityToken` comparison with a
> `400`, forever, with no server-side error. **A silent wedge, not a loud failure.**

And the condition cannot be evaluated from outside the assembly: `IAntiforgeryFeature` is `internal`,
so `NewCookieToken` / `HaveStoredNewCookieToken` are unreadable. Cookie *presence* is observable;
cookie *validity* is not, and presence-without-validity is precisely the wedge case.

One useful property survives: the feature is cached per request and `NewRequestToken` is memoized,
so `GetTokens` followed later in the same request by `GetAndStoreTokens` flushes the pending cookie
token and returns the same `RequestToken`. A hybrid is therefore *possible* — but not steerable
without `internal` access.

**Conclusion: `GetTokens` cannot be the basis of the fix.** Any cache-header remedy must work with
`GetAndStoreTokens`.

## Why the package is not obsoleted by .NET 11

Worth settling, because .NET 11 ships a `CsrfProtectionMiddleware` auto-injected by
`WebApplication.CreateBuilder`, and "just delete the package" is a legitimate question to ask.

It validates only endpoints carrying `IAntiforgeryMetadata` with `RequiresValidation = true` —
Blazor SSR, minimal APIs that bind form data, and MVC actions with `[ValidateAntiForgeryToken]` /
`[AutoValidateAntiforgeryToken]`. The migration guide is explicit:

> Endpoints that bind JSON, such as a plain `MapPost` or a Web API `[HttpPost]` action, have no
> behavioral change.

And `.NET 8/9` added `app.UseAntiforgery()` for *validation* only; there has never been a built-in
way to hand the request token to a SPA. So for the cookie-authenticated JSON API this package
targets, it remains necessary. What changes is that same-origin apps on .NET 11 now get a free
`Sec-Fetch-Site` layer underneath, which the README should mention.

⚠️ One caution for whoever writes that README section: `anti-request-forgery.md` contains a bullet
claiming *"APIs called from cross-origin SPAs can rely on this middleware combined with a CORS
allowlist, and skip the token system entirely"*, which contradicts both the "no behavioral change"
statement and the middleware source (`if (antiforgeryMetadata is null) return _next(context);`).
**Do not build documentation on that bullet.**

## The consumer contract: what Spark actually needs

[MintPlayer.Spark](https://github.com/MintPlayer/MintPlayer.Spark) mints the same cookie itself, at
`libs/spark/MintPlayer.Spark/SparkMiddleware.cs:348-369`, and has declined to adopt this package
twice in writing (`docs/coverage-handoff-plan.md:667-678` and `docs/xsrf_minting_PRD.md` §4), both
times citing only the cookie flags.

Its cookie is **exactly the shape the issue proposes** — `HttpOnly = false`,
`SameSite = SameSiteMode.Strict`, `Secure = context.Request.IsHttps`, `Path = "/"`, null-guarded,
no `Domain`/`Expires`/`MaxAge`.

`XsrfCookieFlagTests` (E2E, real out-of-process Kestrel over `https://localhost:{random-port}`, so
`IsHttps` is genuinely `true`) asserts exactly two things — `Secure` present, `SameSite=Strict` —
plus that the cookie exists. It does **not** assert `HttpOnly`, `Path`, `Domain` or `Expires`.

### Spark's placement A/B is evidence *for* this package

`tests/MintPlayer.Spark.Tests/Extensions/XsrfMintingPlacementTests.cs` drives real Identity
sign-in/out through both placements:

| Protected call immediately after… | `BeforeHandler` (Spark today) | `OnStarting` (this package) |
|---|---|---|
| sign-in | 400 | **200** |
| sign-out | 400 | 400 |
| control: garbage token | 400 | 400 |
| control: no token | 400 | 400 |

Spark mints before the handler, so the token on the sign-in response is bound to the *anonymous*
principal, and Spark needs a `POST /spark/auth/csrf-refresh` round trip to recover. This package's
`OnStarting` placement removes that round trip for sign-in. (Sign-out is unfixable by placement —
`SignOutAsync` never resets `HttpContext.User` — so `/csrf-refresh` stays either way.)

**So the swap is a net upgrade for Spark, not parity**, provided the flags land.

### ⚠️ The gate that would break Spark

`POST /spark/auth/csrf-refresh` returns `Results.Ok()` — an empty, **non-HTML** response, and it
depends entirely on the mint running on it. Spark's shopping list says so directly: *"Mint
unconditionally on every response — 'only if absent' permanently breaks login."*

This collides head-on with the most attractive remedy for defect 5, which is to mint only on HTML
navigation responses. **A `text/html` content-type gate would silently break Spark's sign-in flow.**
Any gate must therefore be either configurable or predicated on something other than content type.
This is [Spike 4](./PLAN-Xsrf-Cookie-Hardening.md#spikes) and [Open decision 2](#open-decisions).

Spark's warmup contract also has to survive: `SparkClient.EnsureAntiforgeryAsync` and
`SparkEndpointFactory.MintAntiforgeryAsync` both `GET /spark` and require **both**
`.AspNetCore.Antiforgery*` and `XSRF-TOKEN` in `Set-Cookie`, throwing otherwise.

## Goals

| # | Goal |
|---|---|
| G1 | The cookie carries `Secure` whenever the request is HTTPS, and an application behind a TLS-terminating proxy can get `Secure` without `UseForwardedHeaders`. |
| G2 | The cookie carries an explicit `SameSite` chosen by the application, not by the browser. |
| G3 | A failure inside the `OnStarting` callback degrades to "no cookie on this response" and is **logged**, instead of producing a bare 500 with every header wiped. Defect C must be survivable. |
| G4 | `Cache-Control` and `Pragma` set by the application survive the mint — specifically, the `Cache-Control` that PR #83 went to the trouble of preserving. |
| G5 | Spark can delete its copy and depend on this package without weakening any flag and without breaking `csrf-refresh`, the warmup contract, or `XsrfCookieFlagTests`. |
| G6 | The documentation stops presenting the missing flags as a decision, and states what the package does *not* protect (notably `AntiforgeryOptions.Cookie.SecurePolicy = None`). |
| G7 | The existing seven tests stop pinning the defect; coverage stays at the 80% project / 80% patch gate. |

## Non-goals

- **Validating anything.** The package issues tokens; `[ValidateAntiForgeryToken]` and
  `app.UseAntiforgery()` validate. That boundary is correct and stays.
- **Fixing `AntiforgeryOptions.Cookie.SecurePolicy`'s `None` default.** Not this package's cookie.
  Document it and move on.
- **Cross-origin SPA support.** Angular's interceptor refuses to attach the header cross-origin in
  every version, so double-submit cross-origin is unreachable by construction. Advise a same-origin
  API.
- **Implementing `Sec-Fetch-Site` validation.** Interesting as defence in depth for the net10.0 TFM;
  out of scope here. See *Out of scope*.
- **Fixing `SpaProxy`'s header clobbering.** `SpaProxy.cs:186,191` assigns rather than appends, so a
  dev-server `Set-Cookie` destroys any eagerly-written upstream cookie. Real, dev-only, and unrelated
  to this cookie (which is appended later, at response start). See *Out of scope*.

## Candidate solutions

Stated as options with trade-offs. The solution phase decides; [Open decisions](#open-decisions)
lists what genuinely needs @PieterjanDeClippel's call.

### O1 — The issue's patch, as written

`Secure = Request.IsHttps`, `SameSite = Strict`, null guard, `try/catch`, static lambda with a
tuple state.

- **For:** small, obviously correct, satisfies Spark's `XsrfCookieFlagTests` today, and is literally
  Spark's own implementation, so it is proven in production.
- **Against:** hardcodes two policy decisions the application should own; ships non-`Secure`
  silently behind a proxy (defect C); leaves G4 entirely unaddressed, so the in-repo conflict with
  prerendering survives; a bare `catch {}` swallows defect C without telling anyone.

### O2 — O1 plus cache-header repair

Snapshot `Cache-Control` and `Pragma` before the call and restore them after, restoring *absence*
rather than empty.

- **For:** three lines; directly addresses G4; keeps the mint unconditional, so Spark is safe.
- **Against:** deliberately overrides a framework security decision. And the decision is not
  baseless — the response now carries a `Set-Cookie`, and a **shared** cache storing that is
  genuinely dangerous. A blanket restore is not safe; it must be paired with a `private` directive
  or restricted to responses that were not shared-cacheable anyway.

### O3 — Options-driven cookie built through `CookieBuilder` ← recommended shape

An `XsrfOptions` with `Name` (default `XSRF-TOKEN`), `Path` (`/`), `SameSite`, `SecurePolicy`
(default `SameAsRequest`), and the cookie built via `CookieBuilder.Build(httpContext)` so it
inherits the framework's exact `Secure` semantics and stays compatible with `UseCookiePolicy`'s
upgrade-only pass. Plus: `try/catch` with an `ILogger` error, a one-time warning on the silent
non-`Secure` case, and an explicit choice on the cache headers.

- **For:** every goal reachable; matches framework convention, so users can predict it; the
  `SecurePolicy` enum makes defect C's interaction expressible; `CookieBuilder` means the package
  stops hand-rolling cookie semantics.
- **Against:** the package currently has no options type and no `AddXsrf()`, so this is new public
  surface on a package whose README explicitly says *"There is no `AddXsrf()`"*. Needs an
  `IApplicationBuilder`-side overload or an `IOptions` registration — a design call in itself.
  `<PublishAot>true</PublishAot>` means the options shape must stay trim-safe.

### O4 — Mint gate (only on HTML navigation responses)

Dissolves defect 5 rather than papering over it: the HTML navigation is the response you want
uncached anyway, and it is where the cookie must land to satisfy Angular's liveness requirement.

- **For:** removes the cache clobber from essentially all API responses; matches Microsoft's own
  sample behaviour.
- **Against:** **breaks Spark's `csrf-refresh`** (non-HTML 200). Leaves prerendered HTML `no-store`,
  which is the painful case for *this* repo. Detection is imperfect — `Response.ContentType` in the
  callback is the most robust signal, `Sec-Fetch-Dest: document` corroborates but is absent on old
  browsers, path matching is brittle for a deep-linked SPA.
- Viable only as an **opt-in**, or combined with O2 for the prerender case.

### O5 — Do nothing about the cache headers, document it

Rejected. `no-store` on every response kills CDN caching of prerendered HTML in a package whose
sibling exists to produce prerendered HTML, and it does so invisibly — the framework's warning only
fires when a pre-existing header was overridden, not when one was created from nothing.

## Decisions taken

Settled with @PieterjanDeClippel after the spikes. This table is the authoritative record.

| # | Decision | Outcome and reasoning |
|---|---|---|
| 1 | `SameSite` default | **`Strict`, configurable.** Analytically it is close to symbolic on the JS-readable half — the server never reads this cookie off the wire — but it matches both the framework's own antiforgery cookie and Spark's existing `XsrfCookieFlagTests` assertion, so Spark swaps with zero configuration. Documented honestly as defence in depth rather than as the thing that makes double-submit work. |
| 2 | Is the mint gated? | **No gate.** Spike 4 settled it: `POST /spark/auth/csrf-refresh` returns an empty non-HTML `Results.Ok()` and is called through Angular's `HttpClient`, so it carries `Sec-Fetch-Dest: empty` — no content-type and no fetch-metadata signal keeps it alive. An HTML gate would silently break Spark's sign-in. The cache clobber is fixed by restoring the headers instead (decision 4). |
| 3 | Options type | **Added.** `XsrfOptions` with a `CookieBuilder` and a cache policy, reached through a new `UseAntiforgeryGenerator(Action<XsrfOptions>)` overload. G1 is unreachable behind a proxy without a `SecurePolicy` knob. The parameterless overload is kept as a separate method rather than gaining a defaulted parameter, so already-compiled consumers keep working. |
| 4 | Cache repair shape | **Restore, forcing `private`.** A response that set no `Cache-Control` of its own keeps the framework's `no-store`, so the token-bearing HTML navigation is still never cached. A value the application did set is restored with `private` forced and `public` dropped, because the response carries a `Set-Cookie`. Default is `PreservePrivate`; `NoStore` restores the old behaviour. **This is a deliberate behaviour change and is release-noted as breaking.** |
| 5 | Drop `[Inject]` for this type | **Yes.** Hand-written constructor; `IAntiforgery` moved to `Invoke(HttpContext, IAntiforgery)` so it is resolved per request instead of captured from the root provider. |
| 6 | Spark swap | **Prepared, not committed.** Nothing in the Spark repository is touched until this package publishes. The full change, its rationale and a verification checklist are filed as an issue on `MintPlayer/MintPlayer.Spark` instead. |
| 7 | Version | **`11.0.0-rc.2` across all six packages**, keeping the solution on one number as the `11.0.0-rc.1` sweep left it. `build-master` pushes with `--skip-duplicate`, so an unbumped package is silently skipped. |

## Risks

| Risk | Mitigation |
|---|---|
| `Secure` on a plain-HTTP deployment silently drops the cookie, and the SPA gets a `400` on every mutation with no server-side error | `SameAsRequest` default never emits `Secure` over HTTP. The one-time warning is what makes the *safe* default non-silent. Test both schemes against the real demo (Spike 3). |
| A `catch {}` hides defect C forever — the app 400s on every mutation and nothing says why | Catch, but **log an error** with the exception. "Degrade to no cookie" is only acceptable if it is loud in the log. |
| Restoring `Cache-Control` re-enables shared caching of a response carrying `Set-Cookie` | Open decision 4 — downgrade to `private, no-cache` rather than restore verbatim. |
| A mint gate breaks Spark's `csrf-refresh` | Spike 4 before any gate is written; un-gated is the default. |
| New public options surface on an AOT-enabled package | Keep the options type a plain POCO, no reflection-based binding in the package itself. Verify `dotnet publish` AOT still succeeds. |
| The seven existing tests are rewritten to match the new behaviour and stop being a regression guard | Each changed assertion gets a comment citing #85, exactly as #83 did when it inverted `Clears_headers_and_status_written_by_the_inner_middleware`. |
| Defect 4's real behaviour is untestable in-process | Accept it. Spike 1 verifies it once, by hand, against the real demo; the unit tests assert the *degradation* (cookie absent, error logged), not Kestrel's 500. |

### One criterion partially met, stated plainly

Criterion 4's **integration** half was not delivered. The unit tests prove the middleware preserves
`Cache-Control`, and the wire captures prove it end to end on a real server — but no test puts
`UseSpaPrerendering` and `UseAntiforgeryGenerator` in the same pipeline. `PrerenderingHarness` fires
its `OnStarting` callbacks itself and is built around `SpaPrerenderingOptions`, so wiring the Xsrf
middleware into it is a harness change rather than a test, and the two packages have no shared test
fixture. The conflict it would guard is now covered from the Xsrf side, and the ordering argument is
recorded in the PRD, but **a future change to prerendering's drop-set could reintroduce the clash
without any test failing.** Worth its own issue.

## Out of scope

Recorded so they are not lost, and so nobody mistakes them for things being quietly deferred to a
follow-up PR — they are genuinely not being done.

- **`SpaProxy`'s wholesale header copy** (`Proxying/SpaProxy.cs:176-200`). `Headers[key] = value`
  assigns, so a dev-server `Set-Cookie` destroys any eagerly-written upstream cookie, and the same
  applies to `Vary`, `Cache-Control` and CSP. Dev-only, unrelated to this cookie's timing. Deserves
  its own issue.
- **`AntiforgeryOptions.Cookie.SecurePolicy` defaulting to `None`.** Framework behaviour, documented
  here, not changed here.
- **`Sec-Fetch-Site` / `Origin` validation as a defence-in-depth option** for the net10.0 TFM, where
  .NET 11's `CsrfProtectionMiddleware` does not exist.
- **`__Host-XSRF-TOKEN` support.** Free hardening against cookie injection from a sibling subdomain,
  but it forces `Secure`, forbids `Domain`, requires `Path=/` — so it is incompatible with a
  non-empty `PathBase` and with plain-HTTP non-localhost dev — and it needs a client-side
  `withXsrfConfiguration({ cookieName: '__Host-XSRF-TOKEN' })`, so it cannot be a default without
  breaking every existing consumer.
- **Consolidating the repo's three near-duplicate fake response features**
  (`AntiforgeryMiddlewareTests.RunnableResponseFeature`, `RedirectTests.RunnableResponseFeature`,
  `PrerenderingTestContext.CallbackFiringResponseFeature`). The first two fire **FIFO**; only the
  third reproduces Kestrel's **LIFO**. The Xsrf suite must move to a LIFO fake to test defect 5 —
  that much is in scope — but unifying all three is not.
